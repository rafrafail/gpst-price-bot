# Операционное руководство

Это руководство описывает процедуры обслуживания бота для администратора.

## Резервное копирование

### Создание бэкапа

Бэкап создается только при **остановленном боте**:

```bash
# 1. Остановите бота (systemd, docker, или Ctrl+C)
# 2. Выполните бэкап
python main.py --backup /путь/к/бэкапам/backup-$(date +%Y%m%d-%H%M%S).sqlite3
```

**Требования:**
- Бот должен быть полностью остановлен (нет активных соединений с БД)
- Целевая директория должна существовать и быть доступной для записи
- Бэкап создается через SQLite backup API (корректно копирует WAL-файлы)
- Файл бэкапа получает права `0600`, директория — `0700`

### Что включает бэкап

- Полная SQLite база данных (users, campaigns, deliveries, ui_state)
- Все черновики, запланированные и исторические рассылки
- Состояния доставки (pending/sent/failed/unknown и т.д.)
- Настройки пользователей (подписки, reachable)

### Что НЕ включает бэкап

- `.env` файл с токенами и секретами
- Файлы конфигурации (config.toml, profile.toml)
- Логи, кэш, временные файлы
- История Git

⚠️ **Важно:** База данных содержит персональные данные пользователей (ID, username, имя). Храните бэкапы в защищённом месте, не передавайте их по незащищённым каналам и не коммитьте в Git.

## Восстановление

### Процедура восстановления

```bash
# 1. Остановите бота
# 2. Сделайте бэкап ТЕКУЩЕГО состояния (на случай ошибки)
python main.py --backup /путь/к/бэкапам/current-before-restore.sqlite3

# 3. Восстановите в НОВЫЙ файл (не перезаписывайте текущую БД!)
python main.py --restore /путь/к/бэкапам/backup-20240115-120000.sqlite3 \
    --restore-to /путь/к/data/restored.sqlite3

# 4. Обновите DATABASE_PATH в .env на новый файл
# 5. Запустите бота
```

### Что происходит при восстановлении

1. Проверяется формат и целостность бэкапа (FK, schema version)
2. Создается новый файл БД по указанному пути
3. **Все запущенные кампании переводятся в безопасное состояние:**
   - `pending/sending/failed` → `unknown` (потенциальные дубли не повторяются)
   - `scheduled/running/paused` → `attention` (требуют ручной проверки)
   - `completed/sent` — **не меняются** (уже доставленные не отправляются повторно)
4. Сбрасываются:
   - UI-состояния (текущий экран, ввод, привязки панелей)
   - Подтверждения запуска рассылок
5. **Сохраняются:**
   - Черновики, контент постов, заметки
   - Пользователи и их настройки (subscribed/reachable)

### Эффект на подписки (важно!)

Отписки, сделанные **после** создания бэкапа, **не восстановятся** автоматически.
Пользователи, которые отписались после бэкапа, в восстановленной базе будут иметь `subscribed=1`.

**Рекомендация:** после восстановления сделайте рассылку-опрос или попросите пользователей подтвердить подписку заново. Автоматического opt-in через `/start` нет — пользователь должен явно включить уведомления в настройках.

### Для другого бота (иначе токен)

`file_id` медиа не переносятся между ботами. Для нового бота используйте чистую базу из стартового комплекта, а не restore пользовательской базы.

## Аварийный порядок действий

1. **Остановите владельцем** бота (systemd stop / docker stop / Ctrl+C)
2. **Сделайте бэкап** текущего состояния: `python main.py --backup ...`
3. **Восстановите** в новый путь: `python main.py --restore OLD --restore-to NEW`
4. **Изолированная проверка:** запустите бота с `BOT_TOKEN=test` и проверьте:
   - `/start` работает
   - Меню открывается
   - Нет автоматических отправок старых кампаний
   - Старые кампании в статусе `attention` или `unknown`
5. **Ручное переключение:** обновите `DATABASE_PATH` в `.env`, запустите бота

⚠️ Никаких автоматических restart/deploy. Каждый шаг — осознанное решение оператора.

## Мониторинг

Проверяйте регулярно:
- Размер БД и WAL-файлов
- Наличие свободного места на диске
- Статусы кампаний в админ-разделе (`/admin` в боте)
- Логи доставки на наличие `unknown` и `blocked`

## Безопасность

- Права файла БД: `0600`
- Права бэкапов: `0600` в директории `0700`
- Не отправляйте БД как документ в Telegram
- Не кладите БД в Git
- При смене токена — новый бот, чистая база

# Telegram Bot Template v2

Небольшой универсальный шаблон Telegram-бота на Python и aiogram 3.22.
**Без обязательного ИИ, OpenRouter, Redis, PostgreSQL и веб-панели.**

В основе — единые правила меню и возврата, сохранение состояния в SQLite и
необязательные рассылки. В качестве простого прикладного примера есть «Мои заметки».
Это кандидат v2 в отдельной ветке, не обновление работающего бота.

## Что получит пользователь

- Одно обновляемое сообщение меню вместо нового сообщения на каждое нажатие.
- `← Назад` возвращает на предыдущий экран, включая страницу списка.
- `🏠 Главное меню` открывает начало, но не останавливает рассылку.
- `Отмена` / `/cancel` закрывает текущий ввод; уже сохранённый черновик не удаляется.
- Предпросмотры и результаты остаются отдельными сообщениями в переписке.
- Черновики, текущий экран и заметки восстанавливаются из базы после перезапуска.
- Старые кнопки от другой панели не выполняют действие: бот предлагает открыть меню.

Базовый сценарий — **личный чат**. В группах входящие сообщения игнорируются; откройте личный чат.
Управление рассылками доступно только ID из `ADMIN_IDS`, с повторной проверкой
прав на каждом действии. Администратор видит и изменяет только свои рассылки.

## Новый редактор рассылок

`Главное меню → 📣 Рассылки → ＋ Создать рассылку`.

Обычное сообщение Telegram становится черновиком: текст, фото, видео или альбом.
Нативное оформление Telegram сохраняется через entities, без сырого MarkdownV2.
В карточке можно менять текст, медиа и ссылочные кнопки, выбирать аудиторию,
смотреть предпросмотр, отправлять себе проверку, запускать сейчас или по времени.
Для ссылочных кнопок используется простой ввод: `Подпись | https://example.com`.
Время вводится как `15.01.2027 14:30` в настроенной часовой зоне.
Прошедшее, несуществующее или неоднозначное при переводе часов время отвергается.

Перед запуском отдельный экран показывает аудиторию, её точное количество и время.
Если состав аудитории изменился между подтверждениями, нужен новый просмотр.
Повторное нажатие запуска не создаёт вторую рассылку.

Есть черновики, запланированные, история, прогресс, пауза/продолжение и
остановка с подтверждением. Пользователь может отписаться в настройках;
`/start` сам по себе не отменяет отписку. Новый пользователь, начавший личный
диалог с ботом, по умолчанию включён в уведомления. Это правило можно изменить
для своего продукта в `Store.register_user` и тестах.

### Что означает результат

- **Доставлено** — Telegram вернул успешный ответ для всех частей этого адресата;
  это не означает, что человек прочитал сообщение.
- **Пропущено** — адресат отписался или отправка была остановлена до его очереди.
- **Заблокировано** — Telegram явно отказал в доступе к чату.
- **Ошибка** — известный отказ; повтор только таких адресатов требует подтверждения.
- **Неизвестно** — например, соединение оборвалось после запроса или процесс
  завершился между HTTP-ответом и записью результата. Автоматического повтора нет,
  чтобы не создавать дубли. Нельзя честно обещать exactly-once через Bot API.

Успешные части длинного сообщения записываются по отдельности: после безопасной
паузы или явного `429 RetryAfter` отправка продолжается с неотправленной части.
Воркер соблюдает общий темп, отдельный интервал для одного чата и паузу `RetryAfter`.
`allow_paid_broadcast=False` выставляется явно: платные рассылки не включаются.
Пауза и остановка не могут отозвать HTTP-запрос, уже отправленный в Telegram.

Альбом содержит 2–10 фото/видео. Для альбома ссылочные кнопки отправляются отдельным
сообщением: Bot API не поддерживает inline-клавиатуру у `sendMediaGroup`.
Длинный текст разбивается с сохранением UTF-16 границ форматирования; слишком длинные
неделимые сущности и некорректные ссылки отклоняются до запуска.

## Установка

Требуется Linux и Python 3.11 или новее. Один процесс на один файл базы;
локальная блокировка препятствует случайному второму запуску. SQLite на локальном
диске; распределённые воркеры и общий сетевой диск этой версией не поддерживаются.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Пример **новой** конфигурации: [`config/template-v2.example`](config/template-v2.example).
Старый `.env.example` относится к v1, для нового запуска его не используйте.
Вручную создайте собственный `.env` в корне проекта по новому примеру и задайте
права `600`. Никогда не коммитьте `.env` и не передавайте токен в URL или командной строке.
Этот репозиторий не содержит рабочего токена v2.

Минимальные настройки:

- `BOT_TOKEN` — токен вашего Telegram-бота; нужен только для живого запуска.
- `ADMIN_IDS` — положительные числовые ID администраторов через запятую.
- `BOT_TITLE` — название в главном меню.
- `BOT_TIMEZONE` — IANA-зона, например `Europe/Moscow`.
- `DATABASE_PATH` — по умолчанию `data/template-v2.sqlite3`.
- `BROADCAST_ENABLED=0` — скрыть и отключить рассылки, сохранив меню и пример заметок.

```bash
# Без сети, токена и создания базы: проверка конфигурации.
.venv/bin/python main.py --check

# Только после настройки собственного тестового бота:
.venv/bin/python main.py
```

Режим по умолчанию — polling: перед ним удаляется webhook **без сброса обновлений**.
Для webhook задайте `BOT_MODE=webhook`, публичный HTTPS `WEBHOOK_URL` и случайный
`WEBHOOK_SECRET` (1–256 символов `A–Z a–z 0–9 _ -`). Прокси должен направлять этот URL
в локальный `/telegram`; по умолчанию слушается `127.0.0.1:8080`.
Секрет проверяется на каждом входящем запросе. Настройка прокси/TLS и установка
systemd-службы не выполняются автоматически.

### Обычный и self-hosted Telegram Bot API

По умолчанию `TELEGRAM_TRANSPORT=cloud`: приложение использует облачный Bot API,
никакие `api_id` и `api_hash` для этого не нужны. Для собственного локального
сервера задайте `TELEGRAM_TRANSPORT=self_hosted` и `LOCAL_BOT_API_URL` (по умолчанию
`http://127.0.0.1:8081`). В этом режиме URL принимается **только на loopback**:
Bot API не публикуется в сеть и при недоступном локальном сервисе бот не начнёт
polling, а завершится с понятной ошибкой.

Готовая минимальная конфигурация сервера лежит в
[`infra/telegram-bot-api/`](infra/telegram-bot-api/README.md). В его отдельный
приватный `.env` пользователь вносит только `TELEGRAM_API_ID` и
`TELEGRAM_API_HASH` из [my.telegram.org](https://my.telegram.org); `BOT_TOKEN`
остаётся в основном приватном `.env` приложения. Переключение делается до
запуска процесса, а не кнопкой в чате: одновременно может работать только один
polling-потребитель этого токена.

Перед первым переходом из облачного API в self-hosted режим остановите бот,
подготовьте контейнер и выполните `.venv/bin/python main.py --logout-cloud`.
Команда читает токен только из `.env`, не из командной строки, и делает
документированный `logOut` в облачном API. Затем сразу запускайте бот в выбранном
режиме. Автоматического fallback между облаком и локальным сервером нет: он может
разделить обновления между двумя транспортами. Чтобы вернуться в облачный режим,
сначала остановите self-hosted процесс **и** локальный Bot API контейнер
(`docker compose down` из `infra/telegram-bot-api`, без `-v`). После успешного
`--logout-cloud` облачный вход недоступен 10 минут — дождитесь этого срока,
поставьте `TELEGRAM_TRANSPORT=cloud` и затем запустите ровно один экземпляр бота.

`TELEGRAM_API_BASE` оставлен только как проверяемая обратная совместимость и
тестовый HTTP-seam. Не используйте его одновременно с `TELEGRAM_TRANSPORT=self_hosted`.
Удалённый сервер по этому legacy-параметру требует HTTPS; HTTP разрешён только
для loopback-адресов тестового или локального Bot API.

## Код и расширение шаблона

```text
main.py                         тонкая точка входа
bot_template/
  config.py                     проверяемая конфигурация
  models.py                     данные контента, рассылки и доставки
  storage.py                    SQLite, транзакции, черновики, снимки адресатов
  navigation.py                 панель, история экранов и ввод
  app.py                        меню, заметки и интерфейс редактора
  content.py                    валидация и разбиение нативного контента
  delivery.py                   отправщик, ограничения темпа, сохранение прогресса
  runtime.py                    polling/webhook, блокировка экземпляра, завершение
  storage_contract.md           контракты хранения
config/template-v2.example      безопасный пример без ключей
tests/                          изолированные проверки
```

Начните свою прикладную функцию с примера заметок: отдельный идентификатор экрана,
рендер `View`, действие в `Application.on_callback` и при необходимости ввод в
`Application.accept_messages`. Переходите через `Navigator.open`, возвращайтесь через
`Navigator.back`; не меняйте меню отдельными `send_message` на каждом нажатии.
При росте функции вынесите её предметную логику в отдельный модуль, а не в ядро
навигации. Не нужен реестр плагинов или новый универсальный фреймворк.
Обязательные тесты: открыть → изменить → назад → вновь открыть → перезапустить,
с проверкой состояния, доступа и реального текста/кнопок исходящего Bot API запроса.
Правила для разработчиков: [`AGENTS.md`](AGENTS.md).

## Проверки

Приёмочный CI — **X-CICD через native MCP**, проект `tg-bot-template`,
репозиторий `rafrafail/tg_bot_template`, основная ветка `master`.
Перед запуском получите полный 40-символьный SHA кандидата (`git rev-parse HEAD`),
проверьте существующие прогоны через
`get_run_by_sha(project_id="tg-bot-template", sha=SHA)` и при отсутствии нужного
прогона вызовите `run_gate(project_id="tg-bot-template", sha=SHA, gate="pr")`.
Сохраните `run_number`; дождитесь результата через `wait_for_run`, затем прочитайте
`get_run(run_number=...)`: проект, SHA, gate, терминальный статус и фактически
выполненные стадии должны совпадать с запросом. Ветка вместо SHA не допускается.
Приёмка требует успешных lint, compileall и **полного pytest без пропусков**
в заранее подготовленном образе с `network=none`, только синтетическими токенами
и изолированными временными БД; имя gate или постановка в очередь этого не доказывают.
В отчёте обязательны проект, SHA, номер прогона, gate, итог, стадии и failed stage
при ошибке. Если MCP/регистрация/образ недоступны, результат — `CI unavailable`,
а не замена внешнего gate локальным запуском.

Регистрация проекта, образ и серверная конфигурация принадлежат X-CICD.
Актуальный результат кандидата проверяется через MCP по номеру прогона и точному
SHA; этот README сам по себе не является свидетельством успешной проверки.
GitHub-hosted CI не является приёмкой. `.github/workflows/tests.yml` сохранён
только для ручной диагностики (`workflow_dispatch`, Python 3.11/3.12), без
автоматических запусков на push/PR; его ручной успех также не заменяет X-CICD.

Локальные команды ниже — дополнительные проверки разработчика, не приёмочный CI:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m ruff check .
.venv/bin/python -m compileall -q bot_template tests main.py
.venv/bin/python -m pytest -q
.venv/bin/python main.py --check
```

`tests/conftest.py` создаёт только родительский каталог настроенного `--basetemp`
до использования `tmp_path`; самим basetemp управляет pytest. Поэтому свежему
клону не требуется заранее созданный `_work/`.

Проверяется настоящий aiogram Dispatcher с настоящими моделями Update/Message,
реальная SQLite и исходящие данные Bot API. HTTP-тесты поднимают временный сервер
на loopback: проходят настоящий polling и защищённый webhook, перезапуск и закрытие
соединений. Это **двойник Telegram**, не доказательство доставки на его серверы.
До живого включения нужен отдельный пользовательский прогон на тестовом токене:
[чек-лист и контракт внешнего gate](docs/V2-ACCEPTANCE.md).

## Переход с v1 и персональные данные

В корне сохранены `core/`, `features/`, `prompts/`, старые JSON и документы v1.
Они **не импортируются и не запускаются** новым `main.py`; AI-клиент в них —
историческая справка, не обязательная часть шаблона. `docs/ARCHITECTURE.md` описывает
старую версию. Автоматического переноса старых пользователей, расписания и базы нет.
Не направляйте `DATABASE_PATH` на старую `bot.db`: используйте отдельную базу v2.
Обнаруженная старая схема `users` отвергается без её изменения.

Сохранённые файлы v1 и история Git до v2 могут содержать старые CSV с персональными данными. Для очистки
истории и оценки возможной утечки токена нужна отдельная процедура; текущая
пересборка не является подтверждением их отсутствия и не перевыпускает ключи.
Не публикуйте старую историю как безопасно очищенную. Новый код не экспортирует
ссылки с токеном и не записывает тело рассылки или raw-исключения в журнал доставки.
База с адресатами и черновиками создаётся с правами `600`; резервные копии также
должны оставаться закрытыми.
